The lesson window

From now on every lesson can sit on top of the live product. This page is probably open in that window right now: drag it by the title bar, resize it from the bottom-right corner, minimize it to the dock, press L to hide or show it.

The window is built from small generic pieces that know nothing about lessons. Only the last piece, LessonWindow, combines them with the router.

1. A named outlet: two pages in one URL

/                              product only
/(lesson:lessons/floating-window)   product + this lesson in the window
/lessons/floating-window            this lesson as a full page
  • app.html has the usual <router-outlet />, and LessonWindow has a second one: <router-outlet name="lesson" />. The part in brackets, (lesson:…), is that outlet's URL.
  • app.routes.ts mounts lessonRoutes twice: once normally, once with outlet: 'lesson'. Same components, same lazy chunks.
  • Links that change only the window: [routerLink]="[{ outlets: { lesson: ['lessons'] } }]". The primary outlet (the product) is left alone. Closing sets the outlet to null.
  • Relative links inside a lesson stay in the outlet they were rendered in. The roadmap uses routerLink="setup", so in the window it opens the lesson in the window, and on the full page it opens it full-page. Absolute links are a trap here: routerLink="/lessons" clicked inside the window keeps (lesson:…) in the URL, so the window stays open. To leave the window, one navigation has to set both outlets: { outlets: { primary: ['lessons', path], lesson: null } }. That's what ↗ does.
  • The page title (document.title) follows the primary outlet only. The window shows its own route's title in the title bar. After every NavigationEnd, LessonWindow finds the lesson branch in router.routerState.snapshot and walks down to its deepest child, past the componentless lessons parent.
  • The product doesn't know any of this exists. ≈ Next.js parallel routes (an @lesson slot) used for the "modal with its own URL" pattern.

2. Two directives that find each other

<dialog nscDraggable [(position)]="position">
  <header nscDragHandle>…</header>
  • An attribute directive adds behavior to an element it doesn't own. ≈ a custom hook that receives a ref, or a jQuery plugin.
  • DragHandle calls inject(Draggable): Angular looks up the element tree and returns the nearest nscDraggable. No inputs, no wiring. ≈ useContext, but scoped to the DOM ancestors.
  • position is a model(): a two-way signal. [(position)]="position" keeps the panel's signal and the directive's in sync. ≈ value + onChange props in one.
  • The position goes to style.translate through a host binding. Pointer moves only set a signal; zoneless Angular repaints once per frame, however many events arrive.
  • setPointerCapture keeps the drag going when the pointer leaves the title bar. The viewport bounds are measured once at drag start, because during a drag the DOM is up to a frame behind the signal.
  • Keyboard: focus the title bar (Tab), then the arrow keys move the window, with Shift for bigger steps.

3. A panel with slots

<app-floating-panel panel-id="lessons" [label]="title()" [(minimized)]="minimized" (closed)="close()">
  <span panel-title>…</span>
  <button panel-actions>‹</button>
  <router-outlet name="lesson" />
</app-floating-panel>
  • <ng-content select="[panel-title]" /> picks the children marked panel-title; the plain <ng-content /> takes the rest. ≈ React's named props holding JSX (title={…}) plus children.
  • panel-id is read with inject(new HostAttributeToken('panel-id')). A static attribute is available in the constructor (inputs aren't yet), so the saved position is known before the first render. No jump.
  • It's a <dialog open>: the open attribute makes it non-modal, the same as calling .show(). No backdrop, no focus trap, the globe behind it stays usable. Later lessons need that.
  • Resizing is plain CSS (resize: both). A ResizeObserver reports the new size so PanelMemory can save it, debounced, in localStorage (with try/catch, since storage can be blocked).
  • Minimizing hides the panel with CSS instead of removing it, so the lesson inside keeps its state (scroll position, inputs).
  • ui/ components avoid ::ng-deep with one exception: the panel styles its projected [panel-actions] buttons, which carry the parent's style scope.

4. The dock: a service as a meeting point

  • The panel and the dock bar live far apart in the tree. A root service (Dock) holds a signal with the minimized windows; the panel adds itself, DockBar renders the list. Same idea as the stores in learn-angular lesson 05.
  • The panel's effect() keeps the dock in sync with minimized. Writing a signal inside an effect is fine here: it's syncing state outward, not deriving it (that would be computed).

5. LessonWindow: the only lesson-specific part

  • Shows itself when the URL has a (lesson:…) part and hides when it doesn't. It reads that from the router state after each navigation. The outlet's own (activate) event wasn't reliable for this: moving between two children of the same parent reported the old route.
  • Previous/next follow the order of lessonRoutes. The ↗ link opens the same lesson as a full page.
  • L toggles the window (ignored while typing in a field), Esc minimizes it.

6. LessonPage: a layout through projection

  • Every lesson is now wrapped in <app-lesson-page eyebrow="Lesson 01">…</app-lesson-page>. The .nsc-lesson styles moved here from styles.scss.
  • Projected markup carries the lesson's style scope, so a normal scoped stylesheet in LessonPage wouldn't reach the h2s inside. It uses ViewEncapsulation.None instead, contained by the nsc-lesson root class.

  • Drag it, resize it, reload: same place and size. Make the browser narrow: it stays on screen.
  • Minimize → a chip in the bottom-left. Click it: back where it was. Esc also minimizes.
  • ‹ › step through lessons; ↗ opens the full page; ✕ or L closes; L again reopens the last lesson.
  • Browser back/forward walks through the window's history too, because it's all in the URL.
